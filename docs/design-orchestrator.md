# Проект: оркестратор поверх gemini-delegate — TaskSpec → Executor → TaskResult

Статус: **проект для обсуждения**, ничего не подключено. Основан на пробах
2026-09-09 (пять ролевых прогонов и проба цикла «гейт → возврат → починка»).
Черновики рядом: [contract.md](contract.md), [worker.py](worker.py),
`schemas/`, [SKILL.v2.md](SKILL.v2.md). Живой скилл не изменён.

## 0. Принятые решения (09.09.2026)

Владелец согласился со всеми рекомендациями раздела 9, с одной поправкой:
скилл тоже называется `ultron`.

| Вопрос | Решение |
|---|---|
| Разведка | делегировать картирование, не делегировать решение |
| Runtime | программа: гейт, объём, цикл в той же сессии, состояние, журнал |
| Режим plan | план, одобрение, та же сессия применяет; diff через Fable не используется |
| Гейт | исполнитель гоняет сам, runtime повторяет независимо; вердикт у runtime |
| Состояние | `~/.ultron/state/<проект>/`, вне репозиториев |
| Имя | утилита `ultron`, скилл переименован в `ultron`; триггеры прежние плюс «через ультрон» |
| `confidence` | убрано из схем |
| Ступени по умолчанию | чтение: flash-high → pro-high; код: pro-high → sonnet-4-6 |
| Стек | Python ≥ 3.10 (на маке 3.10.16), только стандартная библиотека; код и комментарии по-английски, тексты для человека по-русски |
| Как строить | Fable пишет спецификацию, тесты и брифы; исполнитель через `agy` пишет реализацию; приёмка по гейту |

**Фаза 2 выполнена 09.09.2026** по разбору рецензии о грязном дереве: baseline как
снимок всего рабочего состояния, восстановление чужих файлов самим runtime,
гейт независимо от доклада, чистая эскалация с патчем, режим worktree. Детали —
`docs/internals.md`, разделы «Фаза 2» и «Режим worktree». `git checkout`,
`git reset`, `git stash` по дереву пользователя не используются нигде.

## 1. Вердикт по предложению «три слоя»

| Идея | Вердикт | Почему |
|---|---|---|
| Три слоя: политика / runtime / состояние | **взять** | v2-draft уже разделён на процедуру, контракт и скрипт; runtime должен взять на себя гейт, объём и повторы |
| Runtime классифицирует задачу и маршрутизирует | **не брать** | классификация — понимание задачи, это Claude в момент написания spec; скрипту доступна только таблица «роль → модель». LLM-классификатор внутри runtime — лишний вызов на 20–40 тыс. токенов ради решения, которое Claude уже принял |
| Runtime верифицирует | **взять, самое ценное** | гейт, проверка объёма по `git`, проверка схемы — механика, ноль токенов Claude. Проверено пробой цикла |
| `TaskSpec` как JSON | **взять как конверт вокруг брифа** | бриф остаётся прозой — модель читает прозу лучше; JSON нужен runtime: объём, приёмка, бюджет, входы |
| `TaskResult` | **взять, с поправкой** | `changed_files` берётся из `git`, а не из ответа модели; `status` ставит runtime, а не исполнитель |
| Исполнители взаимозаменяемы | **интерфейс да, реализация одна** | `agy` уже мультиплексирует Gemini, Claude Sonnet/Opus и GPT-OSS; второго исполнителя нет и не предвидится. Интерфейс — один метод, реестр плагинов не нужен |
| Переименовать в `agent-orchestrator` | **отложить** | триггер «используй гемини» и привычка владельца; переименовать при появлении второго исполнителя |
| `.agent/tasks/<id>/` из семи файлов | **взять пять из семи** | spec, brief, attempts, gate.log, patch — да; `context.json` и `observations.json` заменяются цепочкой `inputs` |
| Context Filter как отдельный компонент | **уже есть** | это `render` + `show` в worker.py, 80 строк; компонент, но не подсистема |
| `events.jsonl` | **взять как журнал попыток** | одна строка на попытку со всеми полями и есть event log; потребитель — `bench.py` |
| Budget controller | **взять частично** | попытки, ступени, токены исполнителя, минуты — да. «Бюджет дорогих токенов» — нельзя: runtime не видит расход Claude, его считает `bench.py` постфактум |
| Политики в трёх YAML | **не брать** | одна таблица на четыре роли; YAML вне stdlib |

Смена мышления, с которой согласен полностью: Claude работает не с Gemini, а с
`TaskResult`. Поправка: **Claude — роутер, runtime — диспетчер.** Решение «кому»
принимается при написании spec, runtime исполняет политику и ничего не выбирает.

## 2. Архитектура

```
Claude (политика: SKILL.md)
  пишет  spec.json + brief.md            ← решение «что, кому, чем проверить»
  читает compact view (≤ 40 строк)       ← единственное, что попадает в контекст
  решает семантику по diff тронутых файлов

runtime (программа)
  compose   бриф + входы из прошлых задач + шаблон ОТВЕТ роли + строки объёма
  dispatch  роль → исполнитель, модель, схема (таблица, не роутер)
  execute   agy --dangerously-skip-permissions … --json-schema
  check     конверт, схема, объём по git, гейт из spec.acceptance
  loop      возврат в ту же сессию с хвостом гейта; ступень выше по политике
  compact   TaskResult → 40 строк; всё остальное — в состояние
  journal   строка на попытку

state (правда)
  <state>/<проект>/tasks/<id>/ spec.json brief.md attempts.jsonl gate.log patch.diff result.json
  <state>/<проект>/journal.jsonl
```

Что где живёт:

| Слой | Файлы | Размер |
|---|---|---|
| Политика | `SKILL.md` — когда делегировать, роли, как писать spec, как читать результат, когда эскалировать, запреты, доклад | 100–150 строк |
| Контракт | `contract.md` + `schemas/` | как сейчас в черновике |
| Runtime | `orchestrator` (один Python-файл или пакет из 4 модулей: compose, executor, check, view) | 400–600 строк |
| Состояние | вне репозитория, по проектам; исполнитель его не видит | — |

## 3. Контракт

### 3.1 TaskSpec — пишет Claude

```json
{
  "id": "T-03",
  "role": "code",
  "goal": "greet здоровается словом hello",
  "dir": "/abs/repo",
  "brief": "brief-03.md",
  "scope": {"write": ["app/service.py"], "forbid": ["tests/", "tools/", "app/models.py"]},
  "inputs": [{"task": "T-01", "fields": ["map", "facts"]}],
  "acceptance": [{"cmd": "python3 tests/test_service.py && python3 tools/check.py", "expect_exit": 0}],
  "budget": {"attempts_per_tier": 2, "tiers": ["gemini-3.1-pro-high", "claude-sonnet-4-6"], "executor_tokens": 500000, "minutes": 20},
  "executor": {"model": null, "effort": null, "mode": null}
}
```

| Поле | Кто использует | Смысл |
|---|---|---|
| `role` | dispatch | `explore` / `code` / `verify` / `review`; выбор — решение Claude, это и есть маршрутизация |
| `brief` | compose | проза из семи блоков; runtime дописывает шаблон ОТВЕТ роли, строки объёма и запрет на git — Claude их больше не печатает |
| `scope.write` / `forbid` | check | после прогона `git status` сравнивается с объёмом; выход за него — нарушение, возврат «откати» |
| `inputs` | compose | поля результатов прошлых задач вставляются в бриф текстом; Claude только ссылается, не перепечатывает |
| `acceptance` | check | runtime прогоняет сам, независимо от того, прогонял ли исполнитель; хвост в `gate.log`, в контекст — код выхода и 10 строк |
| `budget` | loop | попытки на ступень, ступени, токены исполнителя, минуты; всё измеримо на стороне исполнителя |
| `executor` | dispatch | переопределения политики роли; `mode: plan` — патч текстом |

### 3.2 Бриф — проза, как сейчас

Семь блоков без изменений. Runtime добавляет к брифу:

```
ДАНО ИЗ T-01          ← поля из inputs, текстом
ОБЪЁМ                 ← из scope: менять только …; не трогать …
ОТВЕТ                 ← шаблон роли из contract.md, раздел 5
git не трогать, коммиты не создавать
```

### 3.3 Конверт исполнителя — то, что возвращает `agy`

`status`, `denied_actions`, `structured_output`, `conversation_id`, `usage`,
`num_turns`, `duration_seconds`. Runtime читает конверт, Claude — никогда.

### 3.4 TaskResult — собирает runtime

```json
{
  "id": "T-03",
  "status": "accepted",
  "executor_status": "done",
  "attempts": 2,
  "tier": "gemini-3.1-pro-high",
  "summary": "…",
  "changed_files": ["app/service.py"],
  "claimed_files": ["app/service.py"],
  "checks": {"contract": "ok", "scope": "ok", "gate": {"exit": 0, "attempt": 2}},
  "evidence": [{"id": "e1", "where": "app/service.py:4"}],
  "open_questions": [],
  "next_action": "…",
  "usage": {"executor_in": 51077, "cache_read": 133551, "executor_out": 4037, "seconds": 51},
  "refs": {"state": "…/tasks/T-03", "conversation": "82c2a4db-…"}
}
```

| Поле | Источник | Зачем |
|---|---|---|
| `status` | runtime | `accepted` — контракт, объём и гейт зелёные; `rejected` — бюджет исчерпан, что-то красное; `blocked` — исполнитель просит решение; `failed` — нет ответа, таймаут, лимит токенов |
| `executor_status` | модель | что заявила модель; расходится с `status` — это нормально и видно |
| `changed_files` | `git` | правда о дереве |
| `claimed_files` | модель | заявка; расхождение с `changed_files` помечается |
| `checks` | runtime | по каждой проверке: итог и на какой попытке |
| `evidence` | модель | только id и якорь; выдержки лежат в состоянии |
| `usage` | сумма конвертов | все попытки задачи |

`accepted` не значит «правильно». Семантику решает Claude по diff тронутых
файлов: `orchestrator show T-03 --diff`, сначала `--stat`.

### 3.5 Компактный вид — единственное, что видит Claude

До 40 строк: заголовок (роль, статус, попытки, ступень, секунды, токены),
summary, поля роли в сжатом виде, проверки, evidence как список якорей,
open_questions, next_action. Уже реализовано в worker.py и проверено на пяти
ролях: 12–25 строк на результат против 2–7 тыс. символов сырого ответа.

По запросу: `show --evidence e2`, `show --gate`, `show --diff`, `show --raw`.

### 3.6 Интерфейс исполнителя

```
Executor.run(prompt, dir, model, schema, conversation=None, mode=None, timeout) → Envelope
```

Одна реализация: `agy`. Второй появится, когда появится нужда, а не заранее.

## 4. Цикл runtime

```
compose → dispatch → attempt = 1, tier = 0
loop:
  env = execute()
  contract  = конверт SUCCESS, denied пуст, structured_output по схеме, executor_status в enum
  scope     = git status ⊆ scope.write (для ролей без записи — пусто)
  gate      = acceptance[*].cmd, код выхода, хвост в gate.log
  все зелёные                    → status = accepted; стоп
  executor_status == blocked     → status = blocked; стоп        (нужен человек или Claude)
  attempt < attempts_per_tier    → возврат в ту же сессию: шаблон ниже; attempt += 1
  tier + 1 < len(tiers)          → новая сессия, следующая модель, бриф + summary и хвосты прошлых попыток; attempt = 1
  иначе                          → status = rejected
  лимит токенов или минут         → status = failed (budget)
```

Шаблон возврата, который runtime собирает сам, без Claude:

```
Приёмка не пройдена.
[Гейт: <cmd> — код выхода <n>. Хвост вывода: <10 строк>]
[Изменены файлы вне разрешённого объёма: <список> — откати их.]
[Ответ не по схеме: нет полей <список>.]
Исправь причину в разрешённых файлах (<scope.write>). <forbid> не трогать.
Ответ строго по схеме: changed_files — все тронутые файлы за все попытки.
```

Семантический возврат («гейт зелёный, но сделано не то») runtime написать не
может — его пишет Claude: `orchestrator retry T-03 --message fix.md`, и цикл
проверок запускается снова с той же сессией.

## 5. Что показала проба цикла

Учебный репозиторий, роль `code`, `gemini-3.1-pro-high`. Гейт содержал
проверку, о которой бриф молчал (docstring у функции). Исполнителю запретили
запускать гейт самому, чтобы цикл сработал наверняка.

| Попытка | Что сделал исполнитель | Гейт | Секунд | Вход | Из кэша | Выход |
|---|---|---|---|---|---|---|
| 1 | заменил hi → hello, больше ничего | красный: нет docstring | 19 | 20,1 тыс. | 44,5 тыс. | 1,7 тыс. |
| 2, та же сессия | добавил docstring, объём соблюдён | зелёный | 32 | 31,0 тыс. | 89,0 тыс. | 2,4 тыс. |

Выводы:

- Цикл замыкается без единого токена Claude: хвоста гейта исполнителю хватило.
- `changed_files` во второй попытке отчитан накопительно, как просил шаблон.
- Вторая попытка в той же сессии **не дешевле** первой по входу: контекст
  растёт. Дешевле она только по кэшу (тарифицируется ниже) и по отсутствию
  Claude в цикле. Значит, экономия — на стороне Claude, а не Gemini.
- В боевом режиме исполнитель должен гонять гейт и сам (самокоррекция внутри
  одного вызова дешевле круга), а runtime — прогонять независимо для вердикта.

Из пяти ролевых прогонов ранее: `confidence` всегда 1.00 — поле убрать; патч
из `--mode plan` не применился через `git apply` (модель дописала
несуществующую строку контекста) — режим plan должен применяться той же
сессией после одобрения, а не diff-ом через Fable.

## 6. Состояние и журнал

```
~/.claude/skills/ultron/state/<проект>/
├── journal.jsonl                      строка на попытку: ts, task, role, tier, attempt, model,
│                                      contract, scope, gate, verdict, usage, seconds
└── tasks/T-03/
    ├── spec.json                      как написал Claude
    ├── brief.md                       как ушло исполнителю, после compose
    ├── attempts.jsonl                 конверты agy + проверки runtime, по попытке
    ├── gate.log                       последний прогон приёмки целиком
    ├── patch.diff                     только в режиме plan
    └── result.json                    итоговый TaskResult
```

Почему вне репозитория: исполнитель работает в `--add-dir` и не должен видеть
чужие логи; журнал по проектам совпадает с тем, как сравнивает `bench.py`;
прошлая сессия уже клала журнал в каталог скилла. Альтернатива — `.agent/` в
репозитории под `.gitignore` — решение владельца.

`journal.jsonl` совместим с `bench.py`: поля `agy` на верхнем уровне, остальное
в `_meta`. Это и есть event log: одна строка — одно событие «попытка», из неё
считаются стоимость, ступени, повторы и доля принятых.

## 7. Чего runtime не делает

- Не классифицирует задачи и не выбирает роль: это Claude.
- Не решает семантику: `accepted` — про механику, правильность — по diff.
- Не пишет семантические возвраты: их пишет Claude через `retry --message`.
- Не создаёт коммитов, не трогает историю, не выходит за `dir`.
- Не эскалирует дальше ступеней из `budget.tiers`.
- Не видит расход Claude и не обещает его контролировать.

## 8. Риски и защиты

| Риск | Защита |
|---|---|
| Исполнитель «чинит» гейт, ослабляя тесты | `scope.forbid` на `tests/`; проверка объёма по `git`; возврат «откати» |
| Бесконечный цикл | `attempts_per_tier`, `tiers`, `executor_tokens`, `minutes` |
| Автоэскалация тратит квоту Antigravity на Claude-модели | ступени задаёт spec, по умолчанию две; видно в `tier` результата |
| Исполнитель читает состояние и раздувает контекст | состояние вне репозитория |
| Runtime выполняет произвольную команду из `acceptance` | тот же уровень доверия, что Bash от Claude; команду пишет Claude |
| Compose добавляет строки, которых Claude не видел | `brief.md` в состоянии — ровно то, что ушло; читается по запросу |

## 9. Решения за владельцем

1. Разведка: снимаем запрет на делегирование механической части (T0 → `explore` → Claude по карте)?
2. Режим plan: «план → одобрение → та же сессия применяет» вместо diff через Fable?
3. Runtime как программа (гейт, объём, цикл, состояние) или контракт остаётся текстом, а проверки делает Claude руками?
4. `confidence` убираем?
5. Ступени эскалации по умолчанию: `flash-high → pro-high` для чтения, `pro-high → sonnet-4-6` для кода?
6. Состояние и журнал: в каталоге скилла по проектам или `.agent/` в репозитории?
7. Имя: оставить `gemini-delegate` до второго исполнителя?
8. Исполнитель гоняет гейт сам и runtime повторяет независимо, или гейт только у runtime?

## 10. Фазы, если решения приняты

1. **Ядро.** `orchestrator run|show|retry`, гейт и объём, цикл в той же сессии,
   состояние и журнал. `SKILL.md` — политика на 100–150 строк, `contract.md` —
   контракт. Замер по `bench-protocol.md` на одной реальной задаче.
2. **Цепочки и ступени.** `inputs`, эскалация по `tiers`, лимиты бюджета.
   Замер снова.
3. **Аналитика.** Отчёт по журналу: доля принятых, средние попытки, токены
   по ролям и ступеням. Решение о переименовании и втором исполнителе — по
   этим цифрам, не по диаграмме.
